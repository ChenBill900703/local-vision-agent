# 開發過程與結果：給第一次接手的人

## 一開始要解決的問題

目標是在 RTX 3070 Ti 8GB 的一般個人電腦上，完成一套不依賴雲端的影像理解系統。它不只產生一段描述，還會依照觀察內容補問問題、檢查敘述，並把不確定與停止原因留下來。重點是可控制、可追溯的工程流程，不是先假定它一定比單次回答更準。

較早的 Pet／DTD 分類方向已被作者取代；相關舊程式保留為歷史，不能當成目前主系統。

## 實際做過的階段

| 階段 | 做了什麼 | 實際結果 |
|---|---|---|
| CPU 工程骨架 | 定義輸入、工具、記憶、驗證與停止規則，用 mock 測試 | 建立可執行且有上限的流程；mock 不當成辨識證據 |
| Moondream2 可行性 | 在原硬體做有界載入、影像編碼、英文與中文診斷 | 英文路徑可用；中文會重複問題，最後英文指令要求繁中仍只回英文。保留失敗，停止調 prompt |
| 切換 InternVL3 | 作者授權指定候選，固定 revision，檢查資產與離線執行 | 初次 pilot 有部分能力探測被過度嚴格的文字判準擋住；保留原結果，另外授權能力測試後經作者人工評閱採用 |
| 真實 Agent 整合 | 接上既有監督程序、RPC、GPU guard、報告與清理 | 合成圖片的真實 Agent smoke 通過；不是正式論文實驗 |
| 真實照片開發測試 | 使用作者提供的私人照片 | 室內案例達工具上限而不完整。作者認為整體可用，但保留截斷與未完成驗證 |
| 驗證額度修正 | 依剩餘呼叫額度安排驗證，無額度的 claim 明確列為未解決 | CPU 通過；不以增加呼叫上限來掩蓋問題 |
| 手機原圖輸入 | 原圖先驗證，再自動處理方向、RGB 與縮放 | 原始室外照片的組合開發驗證完成：8 次呼叫、6 次驗證、2 個額度不足未驗證、75% 覆蓋。覆蓋率不是正確率 |
| 工程基線確認 | 作者審閱開發結果 | 接受工程可用性；不存在的杯子、錯誤物件屬性與驗證過度接受仍是負面證據 |
| Windows／Webcam 軟體 | PySide6 介面、FakeCamera、逐張分析、持續模型工作程序、本地歷史 | CPU 與模擬接口驗證通過；不能因此說實體 Webcam 已通過 |
| 資料匯出 | 三份 CSV、描述性摘要、獨立人工評閱與防公式注入 | 180 項 CPU 測試與其他品質檢查通過；JSON 始終是原始資料 |
| 最終硬體收尾 | CPU 前檢通過後列舉相機 | Qt 列出 0 台，因此依規則停止；沒有進行新 GPU 載入或手動＋三幀相機推論 |
| 凍結與備份 | 保存文件、接口、環境清單、Git tag、本地備份 | 以「帶有已知 blocker 的備用研究原型」凍結，而不是宣告完整硬體驗收成功 |

## 哪些結論不能拿來宣稱？

不能宣稱模型不會幻覺、同模型驗證就是正確答案、已完成正式大型 benchmark，或 Webcam 本身構成研究創新。也不能把 CPU mock 的 token、耗時、合成畫面當作實體 GPU 或真實辨識數據。

目前明確缺口是實體相機路徑與真實持續多圖 CUDA 的完整驗證。重新接手時先確認攝影機可被 Qt 看見，再由作者重新授權有界驗證，不要直接重跑或重建整個系統。

## 證據放在哪裡？

GitHub 保存各階段方法、amendment、結果報告、接口、測試及版本歷史。原始私人影像、逐次 raw 執行紀錄、模型資產與本地備份仍留在原電腦，文件中的 artifacts 路徑不是遺失的 GitHub 附件，也不表示可以虛構重建。公開／轉交這些資料需要另外確認權利與授權。

這次上傳另保存最後的純文字 CPU 檢查輸出於 [evidence/final_cpu](evidence/final_cpu/)，它們只證明當時的 CPU 品質檢查，不是硬體成功證據。
